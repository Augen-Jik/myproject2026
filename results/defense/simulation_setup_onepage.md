# 仿真环境设置：一页说明

## 1. 为什么要把模型层和环境层分开

这件事的核心目的，其实就一句话：我们希望比较的是“模型会不会选路”，而不是“模型会不会偷偷改考场”。

如果把红绿灯、事故、封路、车流强度、随机种子这些环境变量也交给模型控制，那么模型就可能不是通过更好的路径规划拿到更低的通行时间，而是通过把测试条件改得更容易来“刷分”。这样一来，实验结果既不公平，也很难复现，答辩时也很难自圆其说。

所以现在的设计是：

- 模型层只负责边权估计和路径选择。
- 环境层负责固定控制 SUMO 里的外生条件。

这样做的好处很直接：

- 公平：所有方法面对同一组环境条件。
- 可复现：同一个场景、同一个 seed，结果链路可以重复恢复。
- 边界清晰：我们能明确说，模型解决的是“路径规划问题”，不是“交通信号控制问题”。

## 2. 场景配置控制哪些变量

当前系统把仿真环境统一收敛到 `scene profile`。每个场景 profile 会固定控制下面这些变量：

- 拥堵速度映射和边速度限制
- 事故边、封闭边、车道缩减
- 红绿灯固定 program / phase
- 背景车流需求强度 `depart_rate`
- reroute 是否启用、周期和阈值
- 随机种子 `simulation_seed`
- `warmup_seconds`
- `evaluation_start_time` / `evaluation_end_time`

也就是说，不同测试场景下，拥堵速度、红绿灯和事故状态确实会动态调整，但这些调整不是模型临时决定的，而是由场景配置预先写死、运行时统一注入 SUMO。

当前 `scene_parameter_table.csv` 已经把 8 个场景的关键设置汇总好了，可以直接作为答辩里的“场景参数总表”展示。

## 3. 模型只影响哪些变量

模型现在只影响两件事：

- 边权 / 路径代价估计
- 基于这些代价的路径选择

模型不能直接改：

- 红绿灯 program 或 phase
- 事故、封路、车道缩减状态
- 车流注入强度
- reroute 周期和阈值
- seed
- warm-up 和 evaluation window

所以模型的角色很纯粹：看懂场景，估计边代价，然后选路。

## 4. Planning Time 和 Travel Time 怎么区分

答辩里这两个时间一定要分开讲。

- `Planning Time (s)`：只统计模型推理时间和路径求解时间。
  - 也就是 `Planning Time (s) = model_infer_time_s + route_solve_time_s`
  - 不包含 SUMO 启动、warm-up、仿真推进，也不包含车辆真实行驶时间。
- `Travel Time (s)`：只统计被评估车辆在 SUMO 里从出发到到达的真实行程时间。

简单说：

- `Planning Time` 看的是系统开销。
- `Travel Time` 看的是路径质量。

这两个指标现在是严格分开的，不能再混成一个字段。

## 5. 为什么当前设置公平、可复现、可答辩

当前设置适合答辩，原因主要有五点：

- 第一，环境变量是场景层固定给定的，不是模型自己改的，所以比较公平。
- 第二，当前 `seed policy` 固定为 `scene_profile_fixed_seed_single_run`，每个场景都有明确 seed，实验可以重复。
- 第三，`warm-up`、`evaluation window`、`vehicle_depart_window` 都是提前规定好的，不会因为模型不同而变化。
- 第四，`reroute_trigger_mode` 固定为 `periodic`，不是模型触发，避免把后续环境行为误当成模型能力。
- 第五，SUMO 注入链路已经做过本地核验，速度限制、TLS 固定、evaluation window gating 和 scene-owned reroute 都能真正进入 live SUMO。

所以我们现在可以比较有底气地说：

“模型只负责估计边权和选路；环境负责固定控制交通条件；最终结果反映的是规划能力，而不是测试条件被模型改写后的假提升。”
