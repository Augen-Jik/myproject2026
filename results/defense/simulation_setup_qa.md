# 仿真环境设置：答辩问答

## Q1. 不同场景下速度和红绿灯会变吗？

会变。

不同场景下，系统会动态调整拥堵速度、事故边、封闭边、车道缩减，以及红绿灯固定 program / phase。比如有些场景会把某些边降速，有些场景会封掉核心路段，还有些场景会把 TLS 固定在特定 phase。

但这里要强调一下：这些变化是“场景变化”，不是“模型自己去改环境”。

## Q2. 这些变化是不是模型决定的？

不是。

这些变化都由 `scene profile` 预先定义，再由 SUMO 注入模块在运行时统一写进仿真环境。模型本身不直接控制速度、红绿灯、事故、封路、seed、warm-up 或 evaluation window。

模型只负责两件事：

- 估计边权
- 选择路径

所以环境怎么变，是场景配置决定的；模型怎么走，是模型决定的。

## Q3. 为什么不让模型直接控制红绿灯？

因为那样实验就不公平了。

如果模型能直接改红绿灯，它就不只是“选路”，而是在“改考场”。这样最后拿到更低的通行时间，我们就很难判断到底是路径规划更好了，还是它把信号控制改得更有利了。

答辩里可以直接这么讲：

“我们希望评估的是模型在固定交通条件下的规划能力，而不是它操纵交通设施的能力。”

这样边界更清楚，结论也更容易站得住。

## Q4. Planning Time 和 Travel Time 的区别是什么？

这个问题很关键，最好直接分两句讲：

- `Planning Time (s)` 是系统花了多少时间做规划，等于 `model_infer_time_s + route_solve_time_s`。
- `Travel Time (s)` 是车在 SUMO 里真正开了多久。

也就是说：

- `Planning Time` 反映系统开销。
- `Travel Time` 反映路径效果。

现在这两个指标已经强制分开，不再混在同一个字段里。

## Q5. reroute 是怎么触发的？

现在的 reroute 是场景层固定控制的，不是模型触发的。

当前协议里，`reroute_trigger_mode = periodic`。意思是仿真每走到固定周期，系统就按场景里写好的 `reroute_period` 和阈值规则去检查要不要重路由。

所以 reroute 的 ownership 在环境层，不在模型层。模型不能自己决定什么时候 reroute，也不能自己改 reroute 阈值。

## Q6. seed 和 warm-up 为什么要固定？

因为这两个东西如果不固定，结果就会飘。

- `seed` 不固定，背景交通流和仿真细节会有随机波动。
- `warm-up` 不固定，不同方法面对的起始交通状态就可能不一样。

这样一来，通行时间变化就可能不是模型能力造成的，而是随机性或者起始条件不同造成的。

所以我们现在把它们都固定下来：

- `seed policy = scene_profile_fixed_seed_single_run`
- `warm-up` 和 `evaluation window` 都由场景配置提前给定

这样实验才公平，也更容易复现实验结果。

## Q7. 这套设置为什么适合答辩直接展示？

因为它的逻辑非常清楚，可以概括成一句话：

“场景层固定环境，模型层只做规划，协议层固定评测规则。”

这样讲有三个优点：

- 老师容易听懂边界在哪里。
- 指标定义不会混。
- 如果被追问公平性和可复现性，我们都有明确回答。

如果要再压缩成一句更口语的话，可以直接说：

“我们没有让模型去改红绿灯、改事故、改 seed，它只能在固定环境里估计代价和选路，所以这个结果是可比、可复现、也可答辩的。”
